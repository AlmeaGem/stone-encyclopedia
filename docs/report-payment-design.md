# 第2段階：販売を始める前の設計と費用確認

現在は静的な無料図鑑・質問／回答確認・架空の固定サンプルだけです。個人向けの選定結果、購入権限、決済、PDF保存、再閲覧は未実装で、販売を開始していません。CSSによる非表示やnoindexを購入権限の保護とは扱いません。

## 費用

今回の実装で新規契約・決済API・有料API・課金は発生させていません。既存の静的プレビューと小さなCSS／HTMLを使用します。

第2段階は未着手です。月額0円は「対象サービスの無料枠内に収まる場合」の候補であり、保証ではありません。Workers／DB／認証／メール／保存量／PDF実行時間の見積もりと上限を提示し、有料プランや従量課金を事前承認なく有効にしません。

Stripeの本番手数料は契約国・通貨・支払方法に応じて確認が必要です。1件あたりの想定費用は `790円 × 手数料率 + 固定料金`。この環境では公式価格の最新確認ができないため、税・返金時の扱いも含め、販売開始前に確定します。ドメインや追加メールサービスも今回購入していません。

参照先：[Workers](https://developers.cloudflare.com/workers/platform/pricing/)／[D1](https://developers.cloudflare.com/d1/platform/pricing/)／[R2](https://developers.cloudflare.com/r2/pricing/)／[Supabase](https://supabase.com/pricing)／[Stripe日本](https://stripe.com/jp/pricing)／[Vercel](https://vercel.com/pricing)

## 購入・権限・結果の流れ

1. 承認済みの選定ルールと石・細かな願望の関連付けを整備する。未設定の関係は推測で割り当てない。ルールの版を結果に保存する。
2. 個別レポートの生成・再閲覧のため、利用者の本人認証と、回答保存への同意・保存期間を定める。現在の画面内だけの回答を無断で送信しない。
3. サーバーが認証ユーザーに紐付く注文を作成し、Stripe Checkoutをサーバーで開始する。クライアントの金額、メールアドレス、任意のpaidフラグは権限の根拠にしない。
4. Webhookはリクエストの生データとStripe署名をサーバーで検証。event IDとCheckout session／payment IDに一意制約を設け、重複・再送・順序逆転に耐える冪等処理にする。注文・商品・790円・通貨・支払状態を照合する。
5. 決済確定と購入権限をDBトランザクションで記録。生成ジョブにも一意キー・リース・再試行上限を持たせ、二重生成を防ぐ。返品・返金・取消時は権限と再閲覧可否を一貫して更新する。
6. 結果APIはアクセスのたびに認証と注文所有者・購入状態を確認。成功ページへの遷移だけで結果を配信しない。結果やPDFはGitHub Pages、公開リポジトリ、公開Storageへ置かない。
7. PDFは非公開保存し、権限確認後だけ短期URL等で提供。結果・購入履歴・個人情報は共有キャッシュへ入れない。セッションはSecure／HttpOnly／SameSite、必要なCSRF対策、レート制限を備える。
8. 購入済み利用者が認証して同じレポートを再閲覧できるようにする。推測困難なURL自体をアクセス制御としない。

## 販売開始までの必須検証

未購入・別ユーザー・未認証・paidパラメーター改変・決済未確定・Webhook再送／署名不正・支払金額違い・返金・ジョブ中断／再試行・期限切れリンクをテストします。問い合わせ窓口、事業者表示、返金規約と個人情報の扱いを整えてから販売の承認を受けます。

## 本番・SEOの確認

現在のプレビューはnoindexとrobotsのDisallowを維持します。デザイン改善を検索公開・販売開始とは扱いません。公開承認、210項目の品質・参考文献・画像ライセンス・法務・本番ドメイン・canonical・sitemap・robots・Search Consoleを確認した後、所有者が本番公開を判断します。
