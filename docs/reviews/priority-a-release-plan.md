## 公開作業の手順（実行には別途承認が必要）

1. 最新main・gh-pagesを取得し、各ブランチが基準から進んでいないか再確認。進んでいれば差分と生成物を再検証する。Pagesの公開元、全ワークフローと待機・実行中のデプロイを確認する。
2. 対象のソース・編集ガイドだけを専用ブランチにまとめる。無関係な調査資料や生成物を混ぜない。ソースPRをmain向けに作り、差分とCIを確認する。
3. 明示的な公開承認後にmain向けPRをマージし、マージ後の正確なmainから `SITE_URL=https://almeagem.github.io BASE_PATH=/stone-encyclopedia PUBLIC_LAUNCH=true PUBLIC_SEARCH_INDEXING=true npm run build` で再生成する。main向けのマージ前後に、現在のPages設定と自動デプロイ・待機中の古い実行を再確認する。
4. 最新gh-pagesと生成物の全ファイルを比較し、対象10ページ以外の本文・画像・URL・リンク・アンカーの意図しない変化がないことを検証。既存の公開専用アセットを消さず、必要なファイルだけ反映する。公開候補と生成物のSHA-256を照合する。
5. gh-pages向けPRを作成し、追加・変更・削除と競合を確認する。問題がなければ公開の明示承認に従ってマージし、GitHub Pagesのデプロイ成功を確認する。Force pushは禁止。

## 問題が発生した場合

復旧参照点は公開直前に再取得して記録する。今回の参照点は `15b8bac72e53348e99a3c3072996a22a92cb2c89`。問題の差分を特定し、必要に応じて公開PRの変更を取り消す新しいrevert PRを作成する。マージコミットのrevertでは親番号を確認し、squash等では実際の公開コミットを対象とする。後から公開された無関係な変更は残し、force pushやブランチの強制巻き戻しは行わない。デプロイ後、復旧対象のページ・画像・リンクを再確認する。ソース側にも同じ修正またはrevertを反映し、後の再ビルドで不具合が戻らないようにする。
