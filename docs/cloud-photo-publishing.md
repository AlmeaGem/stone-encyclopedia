# 管理画面だけで写真を公開する構成

対象は **stone-encyclopediaのみ**。Manager、Supabase、図鑑本文210項目、既存のローカル写真管理を変更・移行しません。PR #1は未マージです。

## 結論と比較

推奨は **GitHub Pagesを維持し、写真だけCloudflareで管理**。初回の接続後、写真更新にGit操作・Actions起動は不要です。写真変更は次のページ読込から反映します。閲覧中の画面を強制更新する仕組みではありません。

| 項目         | GitHub Pages + 写真Workers（今回）                                        | 図鑑もCloudflare Pagesへ移行                  |
| ------------ | ------------------------------------------------------------------------- | --------------------------------------------- |
| 図鑑本文     | 現在の静的サイトのまま                                                    | 同じAstro静的ビルドをPagesへ                  |
| 写真         | Workers + 非公開R2 + D1                                                   | 同左                                          |
| 管理ログイン | 別ホストをAccessで保護・WorkersでもJWT検証                                | 同左                                          |
| 写真更新     | 管理画面「保存して公開」だけ                                              | 同左                                          |
| 本文変更     | 従来のGit/ビルド                                                          | Git/Pagesビルド                               |
| 初回作業     | 写真API接続用に1回ビルドが必要                                            | ドメイン・canonical・転送・SEO移行も必要      |
| 月額の目安   | 小規模なら無料枠内が目標                                                  | 同程度。図鑑配信の無料枠も確認                |
| 注意         | JavaScriptでクラウド写真に差し替え。写真自体のSEOは静的HTML方式より限定的 | 静的ビルドのままなら同じ制約。SSR化は別途設計 |

このため、写真管理の改善を目的とする今回は図鑑サイト全体の移行を行いません。

210枚を平均300KB〜2MBに最適化した場合、現行写真は約63〜420MB。差替え履歴も保持するため累積します。1ページにつき目録1回と実際に表示する画像のリクエストが発生し、画像配信ごとにD1を1行読取します。公開停止を確実に反映するため画像はno-storeです。大量アクセス時はリクエスト数が先に上限に達する可能性があります。

初期予算3万円に対し、このPRのためのサービス契約・支出は **0円**。有料プラン・有料素材・新規ドメインは購入していません。無料運用を保証するものではなく、R2の開始時に請求先登録や従量課金への同意が求められる場合は、**有効化せず先に金額条件を確認**してください。課金リスクが承認されるまではローカル検証のみで利用できます。

Workers Freeのまま、R2/D1利用量を月1回確認し、Cloudflareが提供する通知を設定してください。`UPLOADS_ENABLED=false`で管理者の公開操作を一括停止できますが、これは課金上限設定ではありません。異常なアクセスにはCloudflareの利用可能なレート制限機能を検討し、有料機能を勝手に有効化しないでください。

## 初回に必要なアカウント・設定

APIキー・トークン・パスワードをチャットやリポジトリへ貼り付けないでください。

1. Cloudflareアカウントを作成・ログインし、2段階認証を設定する。
2. Cloudflareで管理できる独自ドメインを用意する（既存のものを優先）。この構成例は `photos-admin.<自分のドメイン>` と `photos-api.<自分のドメイン>` の2ホストを使う。Managerのドメインは使わない。
3. Zero Trust → Access → Applications → Self-hostedで **管理ホストの全パス**を保護する。許可対象を自分のメールアドレスだけにし、メールOTPまたは利用するIdPを設定する。Everyone/Bypassは作らない。短いセッション（例1時間）を推奨。PCとスマホで同じ許可アカウントを使用する。
4. 公開APIホストはAccessの対象にしない（承認済み写真のGETだけを公開）。同じWorkerに2つのCustom Domainを設定する。worker.devとpreview URLは無効のまま。
5. **別の新しい**D1データベースと**非公開**R2バケットを作成する。R2のpublic URL・r2.dev公開を有効にしない。既存の写真やSupabaseへSQLを実行しない。
6. `cloud/photos/wrangler.jsonc`のREPLACEとホスト名を実際の設定にする。Access画面のApplication Audience(AUD) Tag、team domain、自分の許可メールを設定。これらはAPI秘密鍵ではないが、管理運用情報として扱う。
7. 初回の開発担当者がローカルで `npx wrangler login`。ブラウザの正規OAuthで承認する。トークンの共有は不要。最低限の権限を使用する。
8. 新規D1に限って `npx wrangler d1 migrations apply almea-encyclopedia-photos --remote --config cloud/photos/wrangler.jsonc` を実行する。**このPRではリモートSQLは実行していません。**
9. `npx wrangler deploy --config cloud/photos/wrangler.jsonc`。Custom Domainsのルーティング、Access保護、未ログイン拒否を確認する。初期値 `UPLOADS_ENABLED=false`なので公開操作は停止中。
10. ログイン検証後に `UPLOADS_ENABLED=true`で再デプロイする。
11. 公開図鑑ビルドの環境変数 `PUBLIC_PHOTO_API_ORIGIN=https://photos-api.<自分のドメイン>` を設定して**一度だけ**再ビルド・プレビュー公開する。GitHub ActionsならRepository Settings → Secrets and variables → Actions → Variablesへ登録する。これは公開APIのURLであり秘密鍵ではない。
12. 現在mainから手動実行するpreviewワークフローは、main側のworkflowにもこの変数読込が必要。PRを勝手にマージせず、初回だけ利用者が設定済みworkflowを許可するか、ビルド済みプレビューの正規デプロイを行う。このPRのworkflow変更だけで未変更mainの実行環境まで変わったとは報告しない。

workers.devを安易に一般公開して管理画面を運用しないでください。独自ドメインがない場合は、Access対応ホストを準備するところから相談します。

## 日常の操作（初回設定後）

1. 管理用URLにアクセスし、許可メールのログインを行う。スマホも同じURL。
2. 石名かs001〜s210で検索し、石を選ぶ。
3. Mac/PCのファイル、スマホの写真ライブラリ・カメラから画像を選択。JPEG/PNG/WebPをサポート。HEICはJPEG変換後に登録。
4. **実物写真 / イメージ写真**を選択する。イメージ写真は公開カード・詳細のどちらにも小さく表示する。
5. 撮影者、出典URL、元画像URL、正確なCCライセンスまたは自社撮影/個別商用許可、クレジット、写真説明を記入する。許諾記録は管理者だけが閲覧できる。
6. プレビュー、石の種類、掲載・変換の権利を確認し、2つのチェックを入れる。
7. **保存して公開**。図鑑を再読込して写真・クレジットを確認する。普段の登録でCommit/Push/Actionsは不要。
8. 差替えは同じ石を選んで新画像を登録。公開停止・登録削除も同じ画面から操作する。

CC BY/CC BY-SAはWikimedia Commonsのファイル出典ページと正確なバージョンを入力します。CC0も出典と権利者を記録します。商用不可/改変不可/不明な権利は選択肢に含めません。イメージ写真も利用権が必要で、石の同定と区分の正確性は管理者が確認します。

## 既存データ・削除の扱い

- ローカル管理画面・候補・承認済みmanifest・写真ファイルはそのまま。新規クラウド写真だけが固定ID単位で優先表示される。
- クラウド未登録の石は従来の静的写真・色調プレースホルダーを使用する。
- クラウド管理の一覧は210種類を表示するが、ローカル静的写真の存在と「クラウド未登録」は別の状態。ローカル画像を自動移動・再承認しない。
- 公開停止/登録削除はtombstone（非表示状態）を保存し、公開目録からクレジットを除外、画像URLを404にする。古い公開URLも同じ固定IDで状態確認するため停止する。
- 原本・監査履歴の**物理削除は未実装**。誤操作保護のため非公開保持。保存容量が増えるため、保持期間と物理削除の方針は運用開始前に決める。
- 既存のGitHub Pages内にある静的写真ファイルのURL自体はクラウドから削除できない。撤回が必要な古い静的写真は、一度だけ通常のビルドから除外する作業が必要。
- 写真API障害時は既存の静的表示を維持する。クラウド写真は静的ファイルにコピーしない。既存静的写真の権利撤回をAPIの公開停止だけに依存しない。
- イメージ写真のラベルと、色調プレースホルダーの「実物ではない」説明は区別する。

## セキュリティと整合性

AccessのJWTを署名・issuer・audience・期限・許可メールまでWorkersで検証。認証なしで管理HTML・管理APIを返さない。管理ホスト制限、同一Originとカスタムヘッダ必須のPOST、管理データno-store。秘密のAPIキーを公開JSへ入れない。

アップロードはブラウザ内で最大1440px WebPへ変換しEXIFを引き継がない。元画像10MB/4000万画素まで、保存WebP2MBまで。サーバーは形式シグネチャと容量も検証する（完全な画像鑑定機能ではない）。SVG/HTMLは受け付けない。原本取得URLをサーバーから取得せず、SSRFを防ぐ。

R2書込後、D1のバッチで公開参照と履歴を原子的に変更。revision条件で端末間の上書きを拒否。失敗や再送が別端末の写真を上書きしない。DB失敗時の非公開孤立画像は安全のため保持し、後日回収可能。署名付きURLは使用せず、公開中の固定IDだけを公開GETで配信する。非公開許諾メモ・監査履歴・オブジェクトキーは公開APIに出さない。

## 未接続時の検証と公開前の残作業

ローカルD1/R2エミュレーターでアップロード・公開配信・権利情報の維持・更新競合・公開停止・差替え・登録削除を検証します。ブラウザではPCとスマホ幅で操作を確認します。これは実Cloudflareアカウント・実サイトでの公開完了とは区別します。

公開先への接続はアカウント・独自ドメイン・Access許可メール・R2請求条件の確認後。実際に所有権を持つテスト写真1枚を管理画面から登録し、PC/スマホの公開図鑑で確認するところが、接続後の受入テストです。現時点で公開URLへ反映済みとは報告しません。図鑑のnoindex、無料/有料境界、販売準備中は維持します。
